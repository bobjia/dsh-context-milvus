# 场景画像必须与技术栈、业务域无关

## 背景

`AGENTS.md` 第 6 节是随 DSH 工作区自动加载的 agent 行为契约（Layer 1 指令），
其内容会**无条件注入每一次对话**。原版本把它写成了一份具体业务域的画像：

- 声明检索目标是「卫星通信系统基站 / 终端的底层协议栈主机软件（嵌入式 C/C++ 为主）」；
- 预设目录结构为 L1/L2/.../L7 分层 + `cross-layer/` + `port/`；
- 用 PDU / SDU / MIB / SIB / ISR / HARQ / 跨层回调 / 信噪比 等术语定义「你必须能正确指认」的表格；
- 回答纪律要求「必须区分控制面 vs 数据面、ISR 上下文 vs 任务上下文」；
- 6.6 把模型身份固化为「嵌入式卫星通信协议栈仓库的资深协议栈工程师」。

问题不在于这些内容不专业，而在于**画像与工程的实际适用范围不符**：
`dsh-context-milvus`（core / dsh / codex 三包）是通用检索引擎，支持
TypeScript / JavaScript / Python / Java / Go / Rust / C / C++ / C# / Scala / Kotlin
（PHP 走 regex 兜底），检索的目标仓库可以是任意领域。把某一份业务域词汇表
固化进全局指令，会带来两类实际损害：

1. **污染无关仓库的回答**：在非协议栈仓库里，模型会被要求输出 PDU / ISR / 控制面
   这类不存在的术语与边界——即指令本身在诱导幻觉。
2. **误导检索策略**：预设「目标代码是 C/C++、按层分目录」会让人误判 chunk 边界、
   语言支持与目录约定，而这些恰恰是本引擎的规格事实（见第 6.2 节）。

## 决策

**第 6 节改为与技术栈、业务域无关的通用画像：保留「三重身份」的结构，去掉一切领域绑定。**

具体替换：

- 场景描述：由「卫星通信协议栈」改为「目标代码库可以是任意技术栈的软件仓库，
  本文件不预设业务领域」。
- 6.1：目标语言改为**枚举引擎真实支持的语言**（而非假设 C/C++），并明确
  「目标代码组织形态不固定，先按仓库实际情况判断」；本仓库自身的工程纪律
  （core/adapter 边界、ESM only、`--experimental-vm-modules`）保留，但限定为
  「只在你修改检索引擎本身时遵守」。
- 6.2：`C/C++ chunking` → `AST chunking`，语义边界由「函数/结构体/switch-case 状态机」
  泛化为「函数/类/结构体/大型分支结构」；rerank 例子由 `on_rx_xxx` 这类协议栈命名
  泛化为 `handleXxx` / `onXxx` / `xxx_entry`；删除按文件、incremental vs full 的
  规格事实原样保留（它们与被检索语言无关）。
- 6.3：由「业务架构师（卫星通信协议栈）」改为「领域理解者」。表格维度由具体协议
  分层改为**通用关注维度**（领域词汇、核心数据结构、关键运行时实体、模块间交互、
  工程约束、可观测性），并新增一条硬约束：领域词汇必须来自仓库内
  README / docs / 术语表 / ADR / 命名，**不得凭空发明**。
- 6.4：运行时边界由「控制面 vs 数据面 / ISR vs 任务」泛化为
  「同步 vs 异步、请求上下文 vs 后台任务、主线程 vs 工作线程、进程内 vs 跨进程」。
- 6.5：改动的对外接口清单由「协议常量 / PDU 字段 / 状态机迁移」泛化为
  「公开 API 签名、数据模型 / 配置项、常量与枚举、序列化格式」。
- 6.6：身份由「嵌入式卫星通信协议栈工程师」改为
  「资深软件工程师 + 向量化检索规格执行者 + 领域导向的技术顾问」。

## 被否决的方案

- **保留协议栈画像、只删术语**：删掉 PDU / ISR 等词后，剩下的「嵌入式、分层目录、
  控制面/数据面」仍是领域绑定，问题只被稀释而非解决。
- **按仓库自动生成场景画像**（读 README / ADR 动态拼一段领域提示）：这是正确方向，
  但属于插件运行时能力（需要新的生成与注入链路），本次是文档级调整，不应顺手夹带
  一个未设计的功能；记录为后续可选演进。
- **把画像移动到独立的 `docs/` 文档，只在 AGENTS.md 留链接**：AGENTS.md 是随工作区
  自动加载的指令，外链文档不会被自动读取，等于让纪律失效（第 6.4/6.5 节的价值正在于
  每轮都在场）。
- **完全删除第 6 节**：会一并丢掉与业务域无关、且已验证有效的部分——三重身份、
  `路径:符号名` 引用要求、`index_status → search_adr_by_file → find_callers` 改动三连、
  设计取舍先查 ADR。这些是检索质量的抓手，不是业务域内容。
- **为每个目标仓库各写一份 AGENTS.md**：文件是仓库自身资产，检索引擎的分发形态
  （三个 npm 包 + 模板分发，见 `docs/analysis-codex-mcp-port.md`）没有按目标仓库改写
  该文件的链路。

## 隐性约束

- 第 1~5 节（工具表、使用规则、full vs incremental、ADR 规则）**一字未动**：
  它们描述的是引擎的真实契约，与业务域无关。
- 6.2 必须继续与实现保持一致：Milvus schema 字段、COSINE 度量、hybrid 模式的
  `sparse_vector`、两阶段 proportional rerank（pool = `topK × multiplier`）、
  删除按文件重建、incremental 默认——任何一条都不能因为「泛化」而被模糊化。
- 6.1 的语言清单必须与 `packages/core/src/chunker.ts` 的语言注册表和
  `CLAUDE.md` 的「Supported languages」表一致（PHP 是 regex 兜底而非 tree-sitter）。
- 第 6 节不再出现任何具体业务域名词（协议栈 / 卫星 / PDU / ISR / 控制面 /
  数据面 / 跨层 等），grep 这些词应为零命中；否则领域绑定会重新渗入。
- 通用化的方式是**替换绑定，而不是删除纪律**：✅/❌ 条目的数量与强度不得下降。
- 本 ADR 只改文档，不改任何代码路径；`AGENTS.md` 不在任何既有 ADR 的
  `code_anchors` 覆盖范围内（改动前 `search_adr_by_file("AGENTS.md")` 为空）。

## 后果

- 在任意技术栈的目标仓库里，第 6 节给出的都是可执行的通用纪律：先看代码、
  引用 `路径:符号名`、区分运行时边界、改前做影响面三连、设计取舍沉淀到 ADR。
- 模型不再被诱导输出目标仓库中不存在的领域术语；领域认知改为**从仓库自身提取**
  （README / docs / 术语表 / ADR / 命名），这是唯一不会产生幻觉的来源。
- 本仓库作为目标仓库时，6.1 的引擎工程纪律仍然生效，但被明确限定在
  「修改检索引擎本身」的场景，避免把它套到目标代码上。
- 代价：对确实在协议栈仓库里工作的用户，第 6 节不再直接给出分层术语表，
  需由模型从该仓库文档现场建立领域认知——这是准确性换专用性的自觉取舍。
