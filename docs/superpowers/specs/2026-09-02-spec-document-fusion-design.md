# Spec Document Fusion — Design

Date: 2026-09-02
Status: Approved (approach + all design sections confirmed by user)

## Context

`dsh-context-milvus` currently provides three knowledge layers, but they are
disconnected:

| Knowledge layer | Location | Vector-indexed | Code-anchored |
|----------------|----------|:---:|:---:|
| ADR (decision records) | `docs/decisions/ADR-*.md` | ✅ adr_embeddings | ✅ code_anchors |
| Code | `src/` | ✅ code_embeddings | — |
| Brainstorming specs/plans | `docs/superpowers/specs/*.md` | ❌ | ❌ |

The **brainstorming** skill produces design specifications and implementation
plans, saving them to `docs/superpowers/specs/` and `docs/superpowers/plans/`.
These documents are "disconnected" — they live as inert markdown in git, the
vector search (`search_code`) and ADR search (`search_adr`) cannot find them,
and there is no link back to the code they describe.

The user's goal: **keep documented knowledge as close to the code as possible.**
Documentation is human-readable; code is machine-readable. The bridge is to
make specs searchable, code-anchored, and discoverable through the same
infrastructure as ADRs.

## Scope

**Core** (approach B, selected by user):

- Spec/plan documents indexed into the shared `adr_embeddings` Milvus collection
- Code anchors (file paths, symbols, line ranges) generated from spec content
- Post-processing step that automatically detects code references and generates
  YAML frontmatter
- New `index_specs` tool for triggering the post-processing
- `search_adr` results marked with `docType` (`adr` / `spec` / `plan`)
- `index_code` auto-scan of specs/plans directories
- Configuration: `specRoot` and `planRoot` config fields

**Not in scope** (approach C — deferred):

- ❌ Spec decision sections injected into system prompt (constraint injection
  remains ADR-only)
- ❌ Spec–code semantic drift detection
- ❌ Automatic anchor maintenance (check_adr_consistency already covers all
  anchored files)

## Architecture decisions

### Decision 1: Shared collection (adr_embeddings), not separate

Specs and plans are indexed into the same `adr_embeddings` Milvus collection as
ADRs, distinguished by a `doc_type` field (`"adr"` / `"spec"` / `"plan"`).

**docType mapping** (from frontmatter `type` field → Milvus `doc_type`):

| Frontmatter `type` | `doc_type` in Milvus |
|--------------------|---------------------|
| `decision-record`  | `adr` |
| `spec`             | `spec` |
| `plan`             | `plan` |

Rationale:
- Reuses the existing hybrid search pipeline (BM25 + dense vector + RRF)
- Single collection for all decision-related documents
- `search_adr` naturally finds specs alongside ADRs — no new search tool
- Schema migration: `ensureAdrCollection` adds the `doc_type` field as a
  nullable VarChar. Existing ADR chunks get `docType: "adr"` on the next
  incremental re-index (delete + re-insert). A `full` re-index is recommended
  once after upgrade to populate the field for all chunks.

### Decision 2: Multi-root scanning, not a single adrRoot

ADR files live in `docs/decisions/`, specs in `docs/superpowers/specs/`, plans
in `docs/superpowers/plans/`. The indexer scans all three roots independently.

Rationale:
- Each directory has a different filename convention
- Keeps the brainstorming skill's output location unchanged
- Merkle tracker and anchor index are filesystem-path-keyed, so multi-root
  adds no complexity

### Decision 3: Post-processing, not inline speculation

Code anchors are generated by a dedicated post-processing step (`index_specs`)
rather than guessed during the spec-writing phase. The post-processor reads
the finished spec, detects explicit code references (`@file:`, `@symbol:`),
matching path patterns, and backtick-quoted symbol names, then writes the
YAML frontmatter with code_anchors before committing.

Rationale:
- Separation of concerns: brainstorming writes the spec; the fusion layer
  adds the machine-readable annotations
- `dry_run` mode lets the user preview anchors before writing
- Existing frontmatter parser (`parseFrontmatter`) works unchanged

### Decision 4: Following adrEnabled, not a separate toggle

Spec/plan fusion is gated behind the existing `adrEnabled` config flag. When
`adrEnabled` is true, the plugin also scans `specRoot` and `planRoot`.

Rationale:
- Avoids config fragmentation (one switch for all decision-document indexing)
- ADR infrastructure (collection, tools, anchor index) is already up when
  adrEnabled is true — no new startup cost

## Index pipeline

### Current flow (adr-indexer.ts)

```
scan adrRoot → hash files → compute delta → remove deleted → chunk → embed → insert → save tracker + anchor index
```

### Extended flow (multi-root)

```
scan adrRoot (ADR-*.md)
    + scan specRoot (YYYY-MM-DD-*-design.md)
    + scan planRoot (YYYY-MM-DD-*.md, excl. *-design.md)
→ hash all files → compute delta → remove deleted → chunk → embed → insert → save tracker + anchor index
```

The three roots share the same Merkle tracker (file paths are unique across all
roots, so a single tracker works).

### Chunker extension (adr-chunker.ts)

The SECTION_MAP adds English sections commonly found in specs/plans:

```
'Context'              → 'context'
'Scope'                → 'scope'
'Environment findings' → 'environment'
'Architecture decisions' → 'decisions'
'Architecture'         → 'architecture'
'Data flow'            → 'data_flow'
'Error handling'       → 'error_handling'
'Testing'              → 'testing'
'Implementation'       → 'implementation'
'Migration'            → 'migration'
'Deployment'           → 'deployment'
'Open questions'       → 'open_questions'
```

Unmapped headings use their original text as the section label (existing
fallback behavior).

## Anchor generation

### Module: adr-anchor-generator.ts (NEW)

```typescript
interface GenerateResult {
  adrId: string
  frontmatter: AdrFrontmatter
  generated: boolean
  detectedRefs: DetectedRef[]
}

interface DetectedRef {
  file: string
  symbols: string[]
  lines: [number, number]
}
```

### Detection algorithm

All three strategies are **cumulative** — each contributes to the final anchor
set. Duplicates (same file path) are deduplicated, and symbols from different
strategies are merged.

1. **Explicit annotations** (`@file:path`): Direct code references written by
   the author in the spec text. Most reliable source. Optionally followed by
   `@symbol:name` for specific symbols, or `@lines:start,end` for line ranges.
2. **Path pattern matching**: Scan for `src/`, `lib/`, `packages/`, etc.
   prefixed paths that match existing files in the codebase.
3. **Symbol references**: Backtick-quoted identifiers (`` `createAdr` ``)
   matched to nearby file paths (looks backward in the text for the nearest
   applicable file path).

## Tools

### New: index_specs

```typescript
name: 'index_specs'
description: '扫描规格文档目录，为无 frontmatter 的文档生成锚点并索引。'
parameters: {
  path: { type: 'string', description: '指定扫描路径（默认扫描所有 specs 和 plans）' },
  dry_run: { type: 'boolean', description: '仅预览将生成的锚点，不写入文件' },
}
```

Behavior:
1. Scan `specRoot` + `planRoot` for markdown files without YAML frontmatter
2. For each candidate: read content → detect code refs → build frontmatter
3. If `dry_run`: return preview without writing
4. If write: atomically insert frontmatter into each file
5. Run `runAdrIndex` to index the new/changed files into adr_embeddings

### Enhanced: search_adr

Search results include `docType` field. Render distinguishes source types:

```
[结果 1] ADR: SPEC-2026-09-01-xxx (active, spec), 章节: decisions
[结果 2] ADR: ADR-0001-xxx (active, adr), 章节: goal
```

### Enhanced: index_code

`index_code` automatically scans `specRoot` and `planRoot` during ADR indexing
(when `adrEnabled` is true). No separate invocation needed for routine use.

execution time.

## Brainstorming integration

### Post-spec-write hint

The `tools/result` hook in `constraint-injector.ts` is extended to detect
writes that land in `specRoot` or `planRoot`. When detected, it injects a
user-role message:

> 📄 检测到新的规格文档 `docs/superpowers/specs/xxx-design.md`。
> 建议调用 `index_specs` 为其生成 code_anchors 并索引入库，
> 让规格与代码建立链接。

### Documented workflow

The README and AGENTS.md will document the recommended flow:

```
1. brainstorming → produces spec at docs/superpowers/specs/
2. call index_specs → generates frontmatter + code_anchors
3. index_code (or auto) → indexes into adr_embeddings
4. search_adr → can now find this spec alongside ADRs
```
